# Dayly — финансовый помощник студента

Согласованные решения (26.09.2026). Здесь то, что действует между сессиями. Обоснования, примеры и полный алгоритм — в `PROJECT_MAP.md`. Макеты — `design-handoff/README.md`, утверждённый сценарий «Превью 2», экраны 2a–2j.

Главный экран отвечает на вопрос «Сколько я могу потратить сегодня, чтобы денег хватило до следующего поступления?». Дневной лимит показан крупно, баланс вторичен. Пользователь — студент в Беларуси, валюта BYN.

## Правила работы

- Работать только внутри этой папки (`/mnt/project-files/dayly/`).
- Этапы идут строго по плану (`PROJECT_MAP.md`, раздел 7). Делать только текущий этап, без фич и абстракций сверх плана.
- Порядок всегда такой: сначала предложение и согласование, потом реализация.
- После каждого этапа — отчёт: ✅ что сделано, список изменённых файлов, вывод тестов, что планируется дальше. Затем остановиться и ждать «продолжай». Любое утверждение «работает» подтверждать реальным выводом команды.
- Без вопросов можно: создавать и править файлы в этой папке, запускать тесты, проверку типов и dev-сервер.
- Остановиться и спросить перед:
  - установкой зависимостей не из списка ниже;
  - удалением любых файлов;
  - изменением модели данных;
  - любыми внешними действиями (деплой, публикация, git push).
- Работать в одной сессии, без субагентов. Исключение — обновления 1 и 2: Егор разрешил субагентов (28.09.2026, карта обновления 2 — 30.09.2026). Они работают в отдельных git worktree, не пушат и не пишут в тред, в `main` пушит только основная сессия одним обновлением.
- Интерфейс на русском, код и идентификаторы на английском. С пользователем (Егор) общаться по-русски.

## Стек

- PWA: React + TypeScript + Vite. Тесты — Vitest. Данные — `localStorage`. Без сервера, авторизации и интеграций с банками.
- Зависимости: `react`, `react-dom`, `@fontsource/manrope`.
- Dev-зависимости: `typescript`, `vite`, `@vitejs/plugin-react`, `vitest`, `@types/react`, `@types/react-dom`. На этапе 5 добавляется `@playwright/test` для e2e.
- Без UI-библиотек, роутера, стейт-менеджеров, библиотек дат и денег. Иконки — inline SVG. PWA-манифест и service worker пишутся вручную. Линтера нет, проверка типов — `tsc --noEmit`.
- Команды: `npm start` (при первом запуске сам делает `npm install`), `npm test`, `npm run e2e`, `npm run typecheck`, `npm run build`, `npm run preview`. Монтаж не поддерживает симлинки, поэтому в `.npmrc` стоит `bin-links=false` (и `legacy-peer-deps=true` из-за бага npm 10 с peer-зависимостями vitest), а скрипты вызывают `node node_modules/…` напрямую.

## Деньги, даты, формат

- Деньги — целые копейки (`number`, поля `…Kopecks`). Никогда не float.
- Округление: всё, что откладывается (резервы, цели, подушка), — вверх; лимит — вниз.
- Формат суммы: `27,50 BYN`. Тысячи разделяются узким неразрывным пробелом U+202F (`1 020,00`), минус — символ U+2212 (`−19,96`).
- Даты — строки `YYYY-MM-DD` по локальному времени устройства. Время суток хранится только в `createdAt`.

## Модель расчёта

Чистая функция `calculateBudget(data, today)` в `src/domain/`, без зависимостей от UI и хранилища. Полный алгоритм и эталонные числа для тестов — `PROJECT_MAP.md`, раздел 2 (примеры А, Б и В).

1. **Период** — от дня основного поступления (`settings.mainIncomeSourceId`) до дня перед следующим таким же. Если основного поступления нет — месяц от дня `trackingStartDate` (начал 27-го — период с 27-го по 26-е; решение Егора 26.09.2026, в онбординге это «Настрою позже»). Если в месяце нет 29–31-го числа, берётся последний день. Недельное основное поступление (`weekday`) даёт период в неделю. Основным может быть только ежемесячный или недельный доход; разовый (`date`) период не задаёт, тогда тоже месяц от `trackingStartDate`.
2. **Баланс** не хранится: это сумма операций (стартовый баланс и сверка — `adjustment`).
3. **Резервы** задаются на полный период у любой категории (по умолчанию у «Продукты» и «Транспорт»; убранная категория резерва не держит). В первом неполном периоде (учёт начат посреди) бюджет пропорционален оставшимся дням. Траты этих категорий по порядку расходуют резерв, переполнение идёт в лимит. Остаток в конце периода не копится.
4. **Трата из лимита**: обычная категория — вся сумма, резервная — только переполнение, оплата платежа и покупка по цели — 0.
5. **Деньги на начало дня** `B = баланс + траты из лимита за сегодня`.
6. **Ожидаемые поступления** — неподтверждённые вхождения плановых доходов (по числу месяца, дню недели или разовые с `date`) с датой от сегодня до конца периода. Поступление, ожидаемое сегодня, считается доступным. Опоздавшее (дата в прошлом, не подтверждено) не учитывается. Нерегулярные доходы в прогноз не входят.
7. **Неоплаченные платежи** — вхождения текущего периода без операции оплаты, включая просроченные. Платёж бывает по числу месяца, по дню недели (в периоде несколько вхождений) или разовый (`date`). Прошлые периоды не переносятся.
8. **Контрольные точки** — даты ожидаемых поступлений позже сегодня плюс день после конца периода. Для каждой точки `c`: `days = c − today`; `free = B + поступления раньше c − платежи раньше c − ceil(остаток резерва × days / дней до конца периода) по каждому резерву − накоплено по целям к c−1 − подушка к c`; `limit_c = floor(free / days)`.
9. **Дневной лимит** = `max(0, min(limit_c))`. Ограничивающая точка — с минимальным `limit_c`, при равенстве ранняя.
10. **Сегодня:** осталось = лимит − траты из лимита за сегодня, отрицательное значение — перерасход. **Завтра** — тот же расчёт на завтра без трат; поступления, ожидаемые сегодня, считаются пришедшими.
11. **Дефицит**: хоть одна `free < 0` → лимит 0, недостача = наибольшая `−free`, дата — эта точка `c`.
12. **Цель** к дате (`deadline`): накоплено к дню `x` = `initialSaved + ceil((target − initialSaved) × дней от startDate по x / дней от startDate по deadline)`, не больше `target`. Цель процентом (`percent`): накоплено к дню `x` = `initialSaved + Σ ceil(поступление × percent / 100)` по операциям `income` с `startDate` по `x`, не больше `target` (то же правило, что у подушки). В точке `c` процентная цель = `min(target, накоплено к сегодня + Σ ceil(ожидаемое поступление × percent / 100))` по ожидаемым раньше `c`. Вычитается всё накопленное, а не взнос периода. С обновления 2 к накопленному прибавляются движения (п. 23–24).
13. **Подушка**: `fixed` — сумма целиком; `percent` — `base + Σ ceil(поступление × percent / 100)` с `sinceDate`, в прогнозе плюс процент от ожидаемых поступлений раньше `c`. «Взять из подушки X» — движение −X (п. 23).
14. **Подтверждение** поступления или оплаты — операция с `incomeSourceId` или `paymentId` и `plannedDate` (дата вхождения). Вхождения раньше `startDate` источника или платежа и раньше `trackingStartDate` не учитываются.
15. **Перенос с вчера** = `DaySummary` вчера − траты из лимита за вчера. Слой приложения после каждого расчёта записывает `{ today, dailyLimit }` в `DaySummary`.

23. **Движения** (`savingsMoves`): «Положить», «Забрать», «Взять из подушки», «Отложить остаток», «Отправить в копилку», округление — записи со знаком и датой, без операции. `M(x)` — сумма движений банки с датой ≤ x. Процентная цель: `clamp(initialSaved + Σ ceil(поступление × percent / 100) с startDate по x + M(x), 0, target)`. Подушка: `amount + M(x)` или `base + Σ долей с sinceDate + M(x)`, не меньше 0, без потолка; её `targetKopecks` — только для свинки и прогресса.
24. **Цель к дате с движениями**: каждый день m с движениями начинает план заново: `база = накоплено к m − 1 + движения дня m`, остаток до `target` делится на дни с m по дедлайн (вверх). Прошлые дни не меняются; положил — в день уходит меньше, забрал — больше. После дедлайна план требует всю цель.
25. **По расписанию** (`schedule`): `clamp(initialSaved + сумма × вхождений с startDate по x + M(x), 0, target)`, вхождение — число месяца (в коротком месяце последний день) или день недели; в точке `c` — вхождения раньше `c`. **Вручную** (все три null): `clamp(initialSaved + M(x), 0, target)`.
26. **Пределы**: положить — не больше `min(сколько не хватает до цели, наименьшая free точек сегодня)` (`putInMax`); забрать — не больше, чем в банке сейчас (`takeOutMax`), у цели к дате с дня дедлайна — 0. Цель «полна на бумаге» (процентная или по расписанию копит сверх `target`) перед «Забрать» считается заново с сегодня от `target`, поэтому уходит ровно X.
27. **Пересчёт с сегодня** (смена процента, дедлайна, расписания или способа, рычаги процента и расписания): `startDate = сегодня`, `initialSaved = накоплено к вчера − M(вчера)`; процентная подушка так же. Фиксированная подушка «держать N»: `amount = N − M(сегодня)`.
28. **Округление** (`settings.roundUp`, шаг 1 BYN): у траты не на целые BYN `X = ceil(сумма / 100) × 100 − сумма` уходит движением `roundup` в выбранную банку, если она активна и не полна, не больше предела «положить» после траты; дата — день траты. Платежи и покупки по цели не округляются. Удаление траты удаляет округление, изменение суммы пересчитывает его в той же банке.
29. **Прогноз наполнения** (`fillForecast`): к дате — дедлайн; процентная — по плановым поступлениям вперёд (до 3 лет); по расписанию — по вхождениям; полная — сегодня; вручную и без цели — нет. **Свинка** (`piggyFill`): накоплено банками с целью (каждая не больше цели) ÷ сумма их целей; подушка без цели — только в общей сумме.
30. **История копилки** (`savingsHistory`): движения плюс вычисляемые строки — доли процентных банок с каждого поступления и суммы по расписанию, с дня старта банки, только то, что банка реально взяла.
31. **Рычаги**: цель по расписанию — сумма −25 % (вверх до целых BYN), считается заново с сегодня; у банки «вручную» рычага нет; фиксированная подушка −25 % от того, что в ней сейчас.

## Объём MVP

- **Экраны из дизайна:** онбординг 2a–2e (деньги → следующее поступление, которое становится основным → платежи → первый лимит), главная 2f с кольцом, шторка ввода 2g, история 2h, настройки 2i, тёмная тема 2j. Внешний вид, тексты и токены берутся из `design-handoff/README.md`.
- **Добавлено к макетам:**
  - плашки «Стипендия пришла?» и «Общежитие оплачено?»;
  - режим «Доход» в шторке;
  - «Сверить баланс»;
  - экран «Как считается» (по образцу 1f);
  - состояния «перерасход» и «дефицит»;
  - изменение и удаление трат нажатием (с обновления 2; долгий тап тоже работает);
  - формы редактирования в настройках: у целей «Купил» и «Отменить», у подушки «Взять из подушки».
- **Трата за 3 действия:** «+ Трата» → сумма → «Добавить». Категория по умолчанию — последняя использованная. Лимит пересчитывается сразу, без перезагрузки.
- **Пока не делаем:** недельный лимит, несколько счетов, напоминания, синхронизация, банки. После MVP уже добавлены копия данных, свои категории, итоги периода (обновление 1), итог по категориям за период и трата за вчера (обновление 2).

## Обновление 1

Карта — `reports/update-1-map.md` (решения Егора 28.09.2026). Вкладка «Календарь» (доходы и расходы разово или с повтором, прогноз лимита на день), откладывание процентом с каждого поступления и кольцо копилки, «Отложить остаток», итоги периода, «Хочу тратить N» с «Как дотянуть», «Завтра будет…», полоска недели и серия, жёлтое кольцо на 80 %, отмена любой траты, «Ближайшее», новая первая настройка, подсказки, «Что нового», «Настройки → Функции». Задачи: 0 «Модель» (модель v5, расчёт, `UiState.features`), A «Календарь», B «Копилка», C «Главная», E «Знакомство», D — сведение и выкладка.

- **Первая настройка:** один вопрос на экран — деньги, «Откуда приходят деньги?» («Пока нет постоянных» = месяц от старта), когда и с каким повтором, сколько, «Что оплачиваешь регулярно?», «Сколько уходит на продукты и проезд?» (резервы `groceries` и `transport` на полный период, можно пропустить). Платежи настройки сохраняются через `saveEvent` (`src/events.ts`).
- **Доход и расход с повтором** — одна шторка `EventSheet` для календаря и настройки. Расход — это обязательный платёж модели. Новый повторяющийся доход становится основным, если основного нет. Изменение дней повтора начинает новое расписание с изменённого вхождения, изменение названия или суммы действует на все повторы.
- **«Что нового»** видит тот, у кого при запуске уже есть данные и `whatsNewSeen` не равен `update-1`; новым пользователям `whatsNewSeen` ставится в конце настройки, им показываются подсказки первого запуска.
- **«Настройки → Функции»:** выключенная функция только не показывается, данные остаются. Цель по лимиту включается сама, когда задано N.
- Отложенное в цель («Отложить остаток», «Отправить в копилку») обратно не забирается; поэтому сумма ограничена так, чтобы не создать дефицит.
- На экране ниже 770 px (iPhone SE, любой iPhone в Safari или Telegram) карточки «Вчера осталось» и «Прошлый период» свёрнуты: заголовок, текст и две кнопки, выбор цели — после «Отложить…», чтобы круг был виден целиком.

- **Знакомство:** вместо трёх подсказок сразу — по одной в момент события (`pickHomeLesson`, `pickTabLesson` в `src/intro.ts`), «Первая неделя» у новых пользователей (14 дней), «Как устроен Dayly» в «Настройках», «Сохрани копию» раз в 14 дней вне установленного приложения. Под кругом не больше одной карточки: «Что нового» → «Первая неделя» → «Сохрани копию». «Что нового» `update-2` видят те, у кого были данные до обновления.
- Отложенное в банку теперь можно забрать («Забрать», с предупреждением о сдвиге цели); «Положить» не больше свободных денег, удаление ручного движения не должно создать дефицит.

## Окружение

- Папка проекта — облачный rclone-монтаж. `npm install` сюда может идти медленно, потому что создаёт тысячи мелких файлов. Если установка идёт неприемлемо долго, остановиться и спросить пользователя, где держать код.
- HTML-макеты загружают React с unpkg, поэтому в облачном контейнере не открываются. Вся спецификация есть в `design-handoff/README.md`, тексты экранов — в самом HTML.
- В облачном контейнере Playwright и Chromium уже установлены (`PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers`). Не запускать `playwright install`. Версия `@playwright/test` должна совпадать с установленной в контейнере (сейчас 1.56.1), иначе браузер не найдётся.
- E2E (`npm run e2e`) собирает приложение и проверяет критерии MVP и обновлений 1 и 2 на `vite preview` (порт 4173, другой — через `DAYLY_E2E_PORT`, чтобы несколько копий шли одновременно). Профиль Chromium на rclone-монтаже зависает (service worker не регистрируется), поэтому здесь запускать с `DAYLY_E2E_OUTPUT=/tmp/dayly-e2e`.
- Опубликовано на GitHub Pages: https://egoricon.github.io/Dayly/, деплой — `.github/workflows/pages.yml` на каждый пуш в `main`. Сборка с `base: './'`, пути в `index.html`, манифесте и `public/sw.js` относительные, чтобы работать и в корне, и под `/Dayly/`.
- Service worker регистрируется только в сборке (`import.meta.env.PROD`). После изменения списка файлов оболочки поднять версию `CACHE` в `public/sw.js`.
